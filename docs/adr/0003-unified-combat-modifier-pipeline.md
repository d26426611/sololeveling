# 統一戰鬥修飾器管線，取代分散的職業技能/種族特性/套裝/次元調整實作

目前「會影響戰鬥或屬性計算的效果」分散在四個地方、四種寫法：職業技能（style）是 `combat.js` 核心回合函式裡不斷增長的 `if (style === 'xyz')` 字串比對鏈；種族特性是散落在 `inventory.js`/`playerStats.js` 裡的 `Player.race === 'x'` 檢查；套裝加成是 `playerStats.js` 裡的 bonus2/4/6 物件套用邏輯；次元調整（見 ADR 0002）則完全還不存在。

這四者本質上是同一件事——「某個來源想在某個時機修改戰鬥或屬性計算」——卻各自維護一套邏輯。單獨修掉職業技能的 if-chain（改成可插拔的技能註冊表）只解決了四分之一的問題，而次元調整即將需要完全一樣的掛勾能力（傷害計算、承傷、擊殺等時機點）。

決定：把四者統一成一個 Combat Modifier Pipeline。每個效果是一個 Combat Modifier：帶有來源標籤（class / race / set / dimension）與掛載點（屬性計算、傷害計算、承傷、回合開始、擊殺...），由核心戰鬥/屬性計算流程通用地讀取、套用，不再為每個來源寫專用程式碼路徑。新增一個職業技能、一個種族特性、一個套裝加成、或一個次元調整，都是「新增一筆 Combat Modifier 資料」，不是「修改核心迴圈」。

配套決定（疊加規則）：同一數值桶內採加法疊加；只在會直接破壞遊戲的數值（暴擊率、減傷率等）設硬上限，不預先為所有屬性建立乘法/優先權分層規則——問題出現了再處理，不预先過度設計。

取捨：這比只修職業技能的 if-chain 工程量大得多，且是這個階段唯一一項會實際觸及既有 `combat.js`/`playerStats.js`/`inventory.js` 核心邏輯的重構。之所以現在做，是因為次元調整（ADR 0002）馬上就需要同樣的掛勾能力，晚做等於之後要再重構一次。
